## 5. Known limitations

- Sandbox, not stage: one VM, MySQL 8.4 in docker, a moto SES stand-in and a fake IMAP server. No real SES, RDS, OAuth providers or mail sink.
- The stack ran on throwaway databases, not `outreach_ai`.
- The SES stand-in was wired for the whole run, so the "SES down" path (OUT-049) is not exercised.
- Run B is partial (6 of 31 suites); see section 4 for what is unverified.
- api_sweep: 203 cases BLOCKED for lack of declared response schemas.
- reports_platform's rate-limit lockout checks are opt-in and were not run (they would lock the shared client IP).
- Some functional suites contain built-in latency checks (contacts CM-091..094, reports_platform's 25-user mix). They ran as
  part of the functional regression in run A. They are not performance evidence.
